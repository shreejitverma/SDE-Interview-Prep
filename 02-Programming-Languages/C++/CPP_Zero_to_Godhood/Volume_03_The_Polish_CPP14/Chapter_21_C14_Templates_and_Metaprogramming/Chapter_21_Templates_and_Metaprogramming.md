# Chapter 21: Templates and Metaprogramming

> *C++14's template additions are small in number but large in leverage. Variable templates give constants a first-class parameterized form; `std::integer_sequence` makes the compile-time "indices trick" a standard tool for unpacking tuples and parameter packs; the `_t` trait aliases erase the `typename ...::type` noise that made C++11 metaprogramming unreadable; and `std::is_final` closes a hole in the type-traits set.*

Template metaprogramming in C++11 worked but read like assembly: every transformation trait needed `typename X<T>::type`, every compile-time constant was a `static constexpr` member buried in a struct, and unpacking a tuple required hand-rolled index machinery. C++14 polishes all three — without adding a new metaprogramming paradigm — making the same techniques dramatically more legible.

## 21.1 Variable Templates

Before C++14, a parameterized *constant* had to be smuggled in as a static data member of a class template (`std::numeric_limits<T>::max()`) or a `constexpr` function. **C++14 adds variable templates**: a variable can be templated directly, giving each type its own value with clean syntax.

```cpp
// Listing 21.1: a variable template
template <typename T>
constexpr T pi = T(3.1415926535897932385);

// Each instantiation has the precision of its type:
float       pf = pi<float>;        // 3.14159f
double      pd = pi<double>;       // full double precision
long double pl = pi<long double>;  // extended precision
```

The same mechanism produces the now-ubiquitous **trait-value variables**: a boolean (or other) constant indexed by type, replacing `Trait<T>::value` with a plain `Trait_v<T>`.

```cpp
// Listing 21.2: defining a trait-value variable template
template <typename T>
constexpr bool is_pointer_v = std::is_pointer<T>::value;

static_assert(is_pointer_v<int*>,  "");
static_assert(!is_pointer_v<int>,  "");
```

This is exactly the form the standard library adopted for its own `_v` aliases (`std::is_integral_v`, etc.) — **but those standard aliases are C++17**. In C++14 you have the *language mechanism* (variable templates) and write the `_v` helpers yourself, as above, or keep using `Trait<T>::value`. The feature is the variable template; the standard `_v` set is the C++17 application of it.

## 21.2 `std::integer_sequence` and the Indices Trick

`std::integer_sequence<T, Is...>` is a compile-time list of integral constants encoded in a type. Its common specialization `std::index_sequence<Is...>` (= `integer_sequence<std::size_t, Is...>`) carries a pack of indices `0, 1, ..., N-1`, generated by `std::make_index_sequence<N>`. Its purpose is to be a **bridge between the value world and the parameter-pack world**: it turns a count `N` into an expandable pack `0..N-1` you can use to subscript a tuple or array.

```cpp
// Listing 21.3: the indices trick -- apply a function to an unpacked tuple
#include <tuple>
#include <utility>
#include <cstddef>

template <typename F, typename Tuple, std::size_t... Is>
auto apply_impl(F&& f, Tuple&& t, std::index_sequence<Is...>)
    -> decltype(std::forward<F>(f)(std::get<Is>(std::forward<Tuple>(t))...))
{
    // The pack Is... expands to 0, 1, ..., N-1, so this becomes
    //   f(get<0>(t), get<1>(t), ..., get<N-1>(t))
    return std::forward<F>(f)(std::get<Is>(std::forward<Tuple>(t))...);
}

template <typename F, typename Tuple>
auto apply(F&& f, Tuple&& t)
    -> decltype(apply_impl(std::forward<F>(f), std::forward<Tuple>(t),
                std::make_index_sequence<
                    std::tuple_size<std::decay_t<Tuple>>::value>{}))
{
    constexpr std::size_t N = std::tuple_size<std::decay_t<Tuple>>::value;
    return apply_impl(std::forward<F>(f), std::forward<Tuple>(t),
                      std::make_index_sequence<N>{});
}
```

```cpp
// Listing 21.4: calling it
int add3(int a, int b, int c) { return a + b + c; }
auto args = std::make_tuple(1, 2, 3);
int result = apply(add3, args);   // -> add3(1, 2, 3) == 6
```

The pattern is always the same two-function shape: a public function computes the size and manufactures an `index_sequence`, and a private `_impl` overload accepts the sequence purely to **name the pack `Is...`** that drives the expansion. Beyond tuple unpacking, `make_index_sequence` powers compile-time loops over packs, structured-binding-style access, and array initialization from a generator. (`std::index_sequence_for<Ts...>` is shorthand for `make_index_sequence<sizeof...(Ts)>` when you already have a type pack.)

> **Note:** `std::apply` itself became a *standard* function in **C++17**; in C++14 you write the `apply_impl`/`apply` pair above by hand. The reusable primitive C++14 gives you is `integer_sequence`.

## 21.3 Transformation Trait Aliases (`_t`)

C++11 transformation traits returned their result as a nested `::type`, forcing a `typename` disambiguator at every use. A SFINAE constraint or a type transformation therefore drowned in `typename ...::type` noise. **C++14 adds `_t` alias templates** for every standard transformation trait, collapsing `typename Trait<T>::type` to `Trait_t<T>`.

```cpp
// Listing 21.5: _t aliases vs the C++11 spelling
// C++11:
typename std::enable_if<std::is_integral<T>::value, T>::type f(T);
typename std::remove_reference<T>::type        x;
typename std::decay<T>::type                   y;

// C++14:
std::enable_if_t<std::is_integral<T>::value, T> f(T);
std::remove_reference_t<T>                       x;
std::decay_t<T>                                  y;
```

The aliases are mechanical — `template <class T> using remove_reference_t = typename remove_reference<T>::type;` — but the readability gain is decisive in the place they matter most, SFINAE-constrained signatures:

```cpp
// Listing 21.6: SFINAE made readable with enable_if_t
template <typename T,
          typename = std::enable_if_t<std::is_floating_point<T>::value>>
T reciprocal(T x) { return T(1) / x; }
```

Every standard trait with a `::type` result has a corresponding `_t` alias (`decay_t`, `remove_reference_t`, `remove_cv_t`, `add_pointer_t`, `conditional_t`, `common_type_t`, `underlying_type_t`, `result_of_t`, and the rest). Prefer them universally — they are pure noise reduction with no semantic cost. (The parallel `_v` value aliases for the *predicate* traits, by contrast, are C++17; see §21.1.)

## 21.4 `std::is_final`

C++14 added the type trait **`std::is_final<T>`**, which reports whether a class type was declared `final`. It fills a gap in the C++11 traits set and lets generic code detect a sealed class — for instance, to decide whether deriving from it (a common empty-base-optimization technique) is even legal.

```cpp
// Listing 21.7: detecting a final class
#include <type_traits>

struct Sealed final {};
struct Open {};

static_assert(std::is_final<Sealed>::value,  "Sealed is final");
static_assert(!std::is_final<Open>::value,   "Open is not final");
```

A concrete use is guarding the *derive-to-compress* idiom (empty base optimization): a wrapper that inherits from its policy type to elide storage for a stateless policy cannot inherit from a `final` policy, so the trait selects between the inheriting and the member-holding implementation.

```cpp
// Listing 21.8: choosing storage strategy based on is_final
template <typename Policy,
          bool CanDerive = !std::is_final<Policy>::value &&
                            std::is_empty<Policy>::value>
class Holder;   // primary template

// CanDerive == true  -> inherit from Policy (empty base optimization)
// CanDerive == false -> hold Policy as a member
```

As with the other predicate traits, the value is read through `::value` in C++14; the `std::is_final_v` shorthand is C++17.

## 21.5 Professional Insights

**Use variable templates for parameterized constants and your own trait shorthands.** A `template <class T> constexpr T epsilon = ...;` reads better than a function call or a buried static member, and defining `Trait_v<T>` helpers locally gives you the clean `_v` ergonomics in a C++14 codebase years before C++17's standard aliases. Keep them `constexpr` so they fold to immediates.

**`integer_sequence` is the standard answer to "I have a count, I need a pack."** Whenever you must expand over `0..N-1` — unpacking a tuple into a call, initializing an array from a generator, looping over a parameter pack at compile time — reach for `make_index_sequence` and the two-function `_impl` pattern rather than re-deriving bespoke index machinery. It is the reusable primitive `std::apply`, `std::tuple` printing, and structured access are all built on.

**Adopt the `_t` aliases everywhere — there is no downside.** They are pure syntactic relief, and in SFINAE-heavy template code the difference between `typename std::enable_if<C, T>::type` and `std::enable_if_t<C, T>` is the difference between a signature you can read and one you can't. Make their use a style rule.

**Mind the version line on `_v` and `std::apply`.** Variable templates, `integer_sequence`, the `_t` aliases, and `is_final` are all C++14; the *standard* `_v` predicate aliases (`is_integral_v`) and `std::apply` are C++17. In a strict C++14 target, define the `_v` helpers and the `apply` wrapper yourself — the underlying mechanisms are already present.
