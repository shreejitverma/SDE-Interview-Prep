\section{DATABASE INTERNALS (LSM

How RocksDB and LevelDB achieve millions of writes per second.

\hypertarget{the-write-problem}{%
\subsubsection{1. The Write Problem}\label{the-write-problem}}

Random writes to disk (B-Tree update) are slow (IOPS bottleneck).
Sequential writes are fast.

\hypertarget{lsm-tree-log-structured-merge-tree}{%
\subsubsection{2. LSM Tree (Log-Structured Merge
Tree)}\label{lsm-tree-log-structured-merge-tree}}

\begin{itemize}
\tightlist
\item
  \textbf{MemTable:} In-memory sorted structure (SkipList or Red-Black
  Tree).

  \begin{itemize}
  \tightlist
  \item
    Writes go here first (fast RAM access).
  \item
    WAL (Write Ahead Log) on disk for durability.
  \end{itemize}
\item
  \textbf{Immutable MemTable:} When MemTable is full, it becomes
  immutable and is flushed to disk.
\item
  \textbf{SSTable (Sorted String Table):} The flushed file on disk.
  Key-Value pairs sorted by Key.
\item
  \textbf{Compaction:} Background process merges multiple SSTables,
  discarding overwritten/deleted keys (Leveled Compaction).
\end{itemize}

\hypertarget{bloom-filters}{%
\subsubsection{3. Bloom Filters}\label{bloom-filters}}

To read a key, we might have to check \emph{all} SSTables. Slow! *
\textbf{Optimization:} Each SSTable has a Bloom Filter. *
\textbf{Check:} If Bloom says ``No'', key is definitely not in this
file. Skip it.

\hypertarget{memory-mapped-io-mmap}{%
\subsubsection{\texorpdfstring{4. Memory Mapped I/O
(\texttt{mmap})}{4. Memory Mapped I/O (mmap)}}\label{memory-mapped-io-mmap}}

Mapping the SSTable file directly into virtual address space. The OS
manages paging. * \textbf{Benefits:} Zero-copy from disk cache to user
space. * \textbf{Risks:} \passthrough{\lstinline!SIGBUS!} if file is
truncated; lack of control over eviction.
