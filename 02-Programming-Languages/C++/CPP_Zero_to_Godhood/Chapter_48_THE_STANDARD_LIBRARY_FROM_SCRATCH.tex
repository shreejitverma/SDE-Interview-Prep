Managing raw memory, growth, and construction.

\begin{lstlisting}[language={C++}]
template<typename T>
class Vector {
    T* data = nullptr;
    size_t sz = 0;
    size_t cap = 0;
    
public:
    void push_back(const T& val) {
        if (sz == cap) {
            reallocate(cap == 0 ? 1 : cap * 2);
        }
        new (data + sz) T(val); // Placement new
        sz++;
    }
    
private:
    void reallocate(size_t new_cap) {
        T* new_data = static_cast<T*>(::operator new(new_cap * sizeof(T)));
        // Move old elements...
        // Delete old memory...
        data = new_data;
        cap = new_cap;
    }
};
\end{lstlisting}

\hypertarget{implementing-myshared_ptr}{%
\subsection{19.2 Implementing
my::shared\_ptr}\label{implementing-myshared_ptr}}

Understanding the Control Block.

\begin{lstlisting}[language={C++}]
template<typename T>
class SharedPtr {
    T* ptr;
    struct ControlBlock {
        std::atomic<int> ref_count{1};
    } *cb;
    
public:
    SharedPtr(T* p) : ptr(p), cb(new ControlBlock()) {}
    
    SharedPtr(const SharedPtr& other) {
        ptr = other.ptr;
        cb = other.cb;
        if (cb) cb->ref_count++;
    }
    
    ~SharedPtr() {
        if (cb && --cb->ref_count == 0) {
            delete ptr;
            delete cb;
        }
    }
};
\end{lstlisting}

class Singleton {

    void operator=(const Singleton&) = delete;

\hypertarget{chapter-50-odr-adl-and-undefined-behavior}{%
\chapter{Chapter 50: ODR, ADL, and Undefined
Behavior}\label{chapter-50-odr-adl-and-undefined-behavior}}

This chapter deconstructs the most subtle and dangerous aspects of the
C++ language specification. Understanding these rules is what separates
a senior engineer from a novice.

\hypertarget{the-one-definition-rule-odr}{%
\section{50.1 The One Definition Rule
(ODR)}\label{the-one-definition-rule-odr}}

ODR states that a program shall contain exactly one definition for any
variable, function, class type, enumeration type, or template in a given
scope.

\hypertarget{translation-units}{%
\subsection{1. Translation Units}\label{translation-units}}

A translation unit (TU) is the result of preprocessing a single source
file. * \textbf{Variable/Function}: Can be declared in multiple TUs but
defined in only one. * \textbf{Class/Inline}: Can be defined in multiple
TUs as long as the definitions are token-for-token identical.

\hypertarget{violations}{%
\subsection{2. Violations}\label{violations}}

Violating ODR often leads to \textbf{Linker Errors} or, worse,
\textbf{Undefined Behavior} if the linker chooses one of several
conflicting definitions.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{argument-dependent-lookup-adl}{%
\section{50.2 Argument Dependent Lookup
(ADL)}\label{argument-dependent-lookup-adl}}

ADL (also known as Koenig Lookup) allows the compiler to find functions
in the namespaces of their arguments.

\begin{lstlisting}[language={C++}]
namespace MyNamespace {
    struct MyType {};
    void func(MyType) {}
}

int main() {
    MyNamespace::MyType obj;
    func(obj); // OK: ADL finds func in MyNamespace
}
\end{lstlisting}

\hypertarget{the-stdswap-idiom}{%
\subsection{The ``std::swap'' Idiom}\label{the-stdswap-idiom}}

ADL is the reason we write:

\begin{lstlisting}[language={C++}]
using std::swap;
swap(obj1, obj2);
\end{lstlisting}

This allows the compiler to use a custom \passthrough{\lstinline!swap!}
in the object's namespace if it exists, falling back to
\passthrough{\lstinline!std::swap!} otherwise.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{undefined-behavior-ub}{%
\section{50.3 Undefined Behavior (UB)}\label{undefined-behavior-ub}}

UB is code for which the C++ standard imposes no requirements. The
compiler is free to assume UB never happens, leading to aggressive (and
potentially catastrophic) optimizations.

\hypertarget{common-sources-of-ub}{%
\subsection{Common Sources of UB:}\label{common-sources-of-ub}}

\begin{itemize}
\tightlist
\item
  \textbf{Dereferencing NULL}: \passthrough{\lstinline!*ptr!} when
  \passthrough{\lstinline!ptr == nullptr!}.
\item
  \textbf{Out-of-bounds access}: \passthrough{\lstinline!arr[10]!} for
  an array of size 10.
\item
  \textbf{Use after free}: Accessing memory after
  \passthrough{\lstinline!delete!}.
\item
  \textbf{Signed integer overflow}:
  \passthrough{\lstinline!INT\_MAX + 1!}.
\item
  \textbf{Data Races}: Unsynchronized access from multiple threads.
\end{itemize}

  >{\raggedright\arraybackslash}p{(\columnwidth - 0\tabcolsep) * \real{0.06}}@{}}
\toprule
\endhead
\#\#\# Professional Notes: Language Formalisms \\
\#\#\#\# 1. Unspecified vs.~Implementation-Defined Behavior *
\textbf{Unspecified}: The standard provides multiple options, and the
compiler chooses one (e.g., order of argument evaluation). *
\textbf{Implementation-Defined}: The compiler must choose one and
document it (e.g., size of \passthrough{\lstinline!int!}). \\
\#\#\#\# 2. Strict Aliasing Rule Compilers assume that pointers of
different types (e.g., \passthrough{\lstinline!int*!} and
\passthrough{\lstinline!float*!}) do not point to the same memory
location. Violating this with
\passthrough{\lstinline!reinterpret\_cast!} can lead to UB. Use
\passthrough{\lstinline!std::bit\_cast!} (C++20) or
\passthrough{\lstinline!memcpy!} for safe type punning. \\
\bottomrule
\end{longtable}

\hypertarget{professional-notes-subtle-quirks}{%
\subsection{Professional Notes: Subtle
Quirks}\label{professional-notes-subtle-quirks}}

\hypertarget{unspecified-behavior-vs.-ub}{%
\subsubsection{1. Unspecified Behavior
vs.~UB}\label{unspecified-behavior-vs.-ub}}

\begin{itemize}
\tightlist
\item
  \textbf{Order of Evaluation}: The order in which function arguments
  are evaluated is unspecified. \passthrough{\lstinline!f(a++, a++)!} is
  unspecified (but if it modifies the same variable twice, it's UB).
\item
  \textbf{Static Initialization Order Fiasco}: The order in which
  globals in different TUs are initialized is unspecified. Use the
  \textbf{Singleton pattern} or \textbf{Nifty Counter} idiom to solve
  this.
\end{itemize}

\hypertarget{deep-recursion-and-stack-frames}{%
\subsubsection{2. Deep Recursion and Stack
Frames}\label{deep-recursion-and-stack-frames}}

Every recursive call pushes a new frame onto the stack. * \textbf{Stack
Depth}: Limited by the OS (e.g., 8MB on Linux). * \textbf{Godhood
Solution}: Use a manual stack with \passthrough{\lstinline!std::stack!}
on the heap to avoid stack overflow for extremely deep traversals.

\hypertarget{chapter-51-linkage-attributes-and-c-incompatibilities}{%
\chapter{Chapter 51: Linkage, Attributes, and C
Incompatibilities}\label{chapter-51-linkage-attributes-and-c-incompatibilities}}

This chapter covers the rules for how identifiers are shared across
files, how to give hints to the compiler, and the subtle ways C++
differs from its parent language, C.

\hypertarget{linkage-specifications}{%
\section{51.1 Linkage Specifications}\label{linkage-specifications}}

Linkage determines whether a name refers to the same entity across
different scopes or translation units.

\hypertarget{types-of-linkage}{%
\subsection{1. Types of Linkage}\label{types-of-linkage}}

\begin{itemize}
\tightlist
\item
  \textbf{External Linkage}: The name can be referred to from other
  translation units (e.g., non-static global variables, non-inline
  functions).
\item
  \textbf{Internal Linkage}: The name is only visible within its own
  translation unit (e.g., \passthrough{\lstinline!static!} globals,
  variables in anonymous namespaces).
\item
  \textbf{No Linkage}: The name is local to its scope (e.g., local
  variables).
\end{itemize}

\hypertarget{extern-c}{%
\subsection{\texorpdfstring{2.
\texttt{extern\ "C"}}{2. extern "C"}}\label{extern-c}}

Tells the C++ compiler to use C-style linkage (no name mangling). This
is essential for calling C functions from C++ or vice versa.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{c-attributes-...}{%
\section{\texorpdfstring{51.2 C++ Attributes
(\texttt{{[}{[}...{]}{]}})}{51.2 C++ Attributes ({[}{[}...{]}{]})}}\label{c-attributes-...}}

Attributes provide a standardized way to provide extra information to
the compiler to improve optimization or warnings.

\hypertarget{common-attributes}{%
\subsection{Common Attributes:}\label{common-attributes}}

\begin{itemize}
\tightlist
\item
  \passthrough{\lstinline![[nodiscard]]!}: Warns if the return value of
  a function is ignored.
\item
  \passthrough{\lstinline![[maybe\_unused]]!}: Suppresses warnings for
  unused variables.
\item
  \passthrough{\lstinline![[deprecated("reason")]]!}: Marks an entity as
  obsolete.
\item
  \passthrough{\lstinline![[fallthrough]]!}: Signals intentional
  fallthrough in a switch statement.
\item
  \passthrough{\lstinline![[likely]]!} /
  \passthrough{\lstinline![[unlikely]]!} (C++20): Hints to the optimizer
  about branch probability.
\end{itemize}

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{c-incompatibilities}{%
\section{51.3 C Incompatibilities}\label{c-incompatibilities}}

While C++ is mostly a superset of C, there are several ``breaking''
differences.

\hypertarget{implicit-conversions}{%
\subsection{1. Implicit Conversions}\label{implicit-conversions}}

\begin{itemize}
\tightlist
\item
  \textbf{C}: Allows implicit conversion from
  \passthrough{\lstinline!void*!} to any other pointer type.
\item
  \textbf{C++}: Requires an explicit cast.
\end{itemize}

\hypertarget{struct-definitions}{%
\subsection{2. Struct Definitions}\label{struct-definitions}}

\begin{itemize}
\tightlist
\item
  \textbf{C}: Requires the \passthrough{\lstinline!struct!} keyword
  every time you refer to the type (unless
  \passthrough{\lstinline!typedef!}'d).
\item
  \textbf{C++}: The struct name becomes a type name automatically.
\end{itemize}

\hypertarget{functions-with-no-arguments}{%
\subsection{3. Functions with No
Arguments}\label{functions-with-no-arguments}}

\begin{itemize}
\tightlist
\item
  \textbf{C}: \passthrough{\lstinline!int func()!} means a function
  taking an \emph{unspecified} number of arguments.
\item
  \textbf{C++}: \passthrough{\lstinline!int func()!} means a function
  taking \emph{no} arguments (equivalent to
  \passthrough{\lstinline!int func(void)!}).
\end{itemize}

\#\#\# Professional Notes: Linking \& Tooling \\
\#\#\#\# 1. Static vs.~Dynamic Linking * \textbf{Static}: Object code is

Mastering the C++ ecosystem requires knowledge of how to manage
large-scale projects and automate the compilation of millions of lines

\hypertarget{the-build-process-architectural-view}{%
\section{52.1 The Build Process (Architectural

A build system automates the invocation of the compiler, assembler, and
linker.

\hypertarget{makefile-the-foundation}{%
\subsection{1. Makefile (The
Foundation)}\label{makefile-the-foundation}}

\passthrough{\lstinline!make!} uses a dependency graph to determine
which files need recompilation. It only rebuilds files whose source has
changed.

\begin{lstlisting}[language=make]
# Simple Makefile
app: main.o utils.o
    g++ -o app main.o utils.o

main.o: main.cpp
    g++ -c main.cpp

utils.o: utils.cpp
    g++ -c utils.cpp
\end{lstlisting}

\hypertarget{cmake-the-modern-standard}{%
\subsection{2. CMake (The Modern
Standard)}\label{cmake-the-modern-standard}}

CMake is a ``Meta-build'' system. It generates Makefiles, Ninja files,
or Visual Studio solutions from a high-level
\passthrough{\lstinline!CMakeLists.txt!}.

\begin{lstlisting}
cmake_minimum_required(VERSION 3.10)
project(MyProject)
add_executable(app main.cpp utils.cpp)
\end{lstlisting}

\hypertarget{linker-errors-common-traps}{%
\section{52.2 Linker Errors (Common
Traps)}\label{linker-errors-common-traps}}

Linker errors happen after successful compilation when the linker cannot
resolve symbols.

\hypertarget{undefined-reference-to-x}{%
\subsection{\texorpdfstring{1.
\texttt{undefined\ reference\ to\ \textquotesingle{}X\textquotesingle{}}}{1. undefined reference to 'X'}}\label{undefined-reference-to-x}}

The compiler saw a declaration of \passthrough{\lstinline!X!}, but the
linker couldn't find its definition. * \textbf{Cause}: Missing source
file in build, missing library in link command, or signature mismatch
(e.g., \passthrough{\lstinline!const!} mismatch in parameters).

\hypertarget{multiple-definition-of-x}{%
\subsection{\texorpdfstring{2.
\texttt{multiple\ definition\ of\ \textquotesingle{}X\textquotesingle{}}}{2. multiple definition of 'X'}}\label{multiple-definition-of-x}}

Violates the One Definition Rule (ODR). * \textbf{Cause}: Defining a
non-inline function in a header file included by multiple TUs. *
\textbf{Fix}: Add \passthrough{\lstinline!inline!} or move definition to
a \passthrough{\lstinline!.cpp!} file.
