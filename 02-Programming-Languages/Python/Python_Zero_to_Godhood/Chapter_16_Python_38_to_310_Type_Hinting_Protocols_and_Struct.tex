\hypertarget{nominal-vs.-structural-subtyping}{%
\subsection{16.1 Nominal vs.~Structural
Subtyping}\label{nominal-vs.-structural-subtyping}}

Python type hints support two distinct typing paradigms: Nominal
Subtyping and Structural Subtyping (implemented via \textbf{Protocols} /
PEP 544).

\hypertarget{nominal-subtyping}{%
\subsubsection{1. Nominal Subtyping}\label{nominal-subtyping}}

Nominal subtyping resolves type compatibility based on explicit
inheritance hierarchies. A class \passthrough{\lstinline!Dog!} is
considered a subtype of \passthrough{\lstinline!Animal!} if and only if
it explicitly inherits from it:

\begin{lstlisting}[language=Python]
class Animal:
    def breathe(self) -> None:
        pass

class Dog(Animal):  # Explicitly nominal
    pass
\end{lstlisting}

Under this model, even if a class defines all methods of
\passthrough{\lstinline!Animal!}, static type checkers will reject it if
there is no explicit base class relationship.

\hypertarget{structural-subtyping-static-duck-typing}{%
\subsubsection{2. Structural Subtyping (Static Duck
Typing)}\label{structural-subtyping-static-duck-typing}}

Structural subtyping resolves type compatibility based on the structure
(methods and attributes) of the class rather than its name. This is
defined using \passthrough{\lstinline!typing.Protocol!}:

\begin{lstlisting}[language=Python]
from typing import Protocol

class Renderable(Protocol):
    def render(self) -> str:
        ...

class Book:
    # Book does NOT explicitly inherit from Renderable
    def render(self) -> str:
        return "Book Text"

def display(item: Renderable) -> None:
    print(item.render())

# Static type checkers accept this call
display(Book())
\end{lstlisting}

Type checkers verify that the interface \passthrough{\lstinline!Book!}
implements all attributes and methods declared in the protocol
\passthrough{\lstinline!Renderable!} with matching signatures and types.

\hypertarget{runtime-protocols-runtime_checkable}{%
\subsection{\texorpdfstring{16.2 Runtime Protocols \&
\texttt{@runtime\_checkable}}{16.2 Runtime Protocols \& @runtime\_checkable}}\label{runtime-protocols-runtime_checkable}}

By default, protocols are static constructs erased during compilation.
At runtime, evaluating
\passthrough{\lstinline!isinstance(Book(), Renderable)!} raises a
\passthrough{\lstinline!TypeError!}. However, decorating a protocol with
\passthrough{\lstinline!@runtime\_checkable!} enables standard runtime
checks.

\hypertarget{the-_protocolmeta-metaclass-internals}{%
\subsubsection{\texorpdfstring{1. The \texttt{\_ProtocolMeta} Metaclass
Internals}{1. The \_ProtocolMeta Metaclass Internals}}\label{the-_protocolmeta-metaclass-internals}}

When a class inherits from \passthrough{\lstinline!typing.Protocol!},
CPython uses the custom metaclass
\passthrough{\lstinline!typing.\_ProtocolMeta!}
(\passthrough{\lstinline!Lib/typing.py!}). 1. \textbf{Attribute
Collection}: During class creation,
\passthrough{\lstinline!\_ProtocolMeta!} scans the namespace dict and
parent MRO to collect all declared non-dunder attributes (methods,
properties, and variable annotations). 2. \textbf{Caching}: It caches
these names in a private set on the class structure named
\passthrough{\lstinline!\_protocol\_attrs!}.

\hypertarget{metaclass-dunder-overrides}{%
\subsubsection{2. Metaclass Dunder
Overrides}\label{metaclass-dunder-overrides}}

\passthrough{\lstinline!@runtime\_checkable!} overrides the dunder
methods of \passthrough{\lstinline!\_ProtocolMeta!}: *
\textbf{\passthrough{\lstinline!\_\_instancecheck\_\_!}}: Overrides
\passthrough{\lstinline!isinstance()!}. *
\textbf{\passthrough{\lstinline!\_\_subclasscheck\_\_!}}: Overrides
\passthrough{\lstinline!issubclass()!}.

\hypertarget{cpython-__subclasscheck__-protocol-logic}{%
\paragraph{\texorpdfstring{CPython \texttt{\_\_subclasscheck\_\_}
Protocol
Logic:}{CPython \_\_subclasscheck\_\_ Protocol Logic:}}\label{cpython-__subclasscheck__-protocol-logic}}

\begin{lstlisting}[language=Python]
def __subclasscheck__(cls, subclass):
    if not isinstance(subclass, type):
        raise TypeError("issubclass() arg 1 must be a class")
    
    # Fast path: nominal subclass checks
    if super().__subclasscheck__(subclass):
        return True
        
    # Slow path: structural MRO checking
    for attr in cls._protocol_attrs:
        # Check if attribute exists in the subclass dictionary or any of its MRO parents
        for entry in subclass.__mro__:
            if attr in entry.__dict__:
                break
        else:
            return False  # Attribute missing in the entire MRO chain
    return True
\end{lstlisting}

\hypertarget{critical-runtime-considerations}{%
\paragraph{Critical Runtime
Considerations:}\label{critical-runtime-considerations}}

\begin{quote}
{[}!WARNING{]} * \textbf{Omission of Type Safety}: Runtime
\passthrough{\lstinline!isinstance!} checks only verify the
\textbf{existence} of the attribute names. They do not inspect method
signatures, parameter counts, or variable types. A class implementing
\passthrough{\lstinline!def render(self, a, b): pass!} will successfully
pass an \passthrough{\lstinline!isinstance(obj, Renderable)!} check,
even though it violates the protocol signature statically. *
\textbf{Performance Penalties}: Traversing the
\passthrough{\lstinline!\_\_mro\_\_!} and inspecting
\passthrough{\lstinline!\_\_dict\_\_!} for every protocol attribute
introduces considerable execution overhead. Avoid using runtime protocol
checks inside critical loops.
\end{quote}

\hypertarget{static-type-checking-and-variance}{%
\subsection{16.3 Static Type Checking and
Variance}\label{static-type-checking-and-variance}}

Static type checkers compile type annotations into a directed graph of
subtypes to enforce type boundaries. The relationships between generic
types depend on \textbf{Variance}.

\hypertarget{mathematical-definition-of-variance}{%
\subsubsection{1. Mathematical Definition of
Variance}\label{mathematical-definition-of-variance}}

Let \(A\) and \(B\) be types where \(A\) is a subtype of \(B\)
(\(A \subseteq B\)). Let \(F\) be a generic container type constructor
(e.g., \passthrough{\lstinline!List[T]!},
\passthrough{\lstinline!Iterable[T]!}, or
\passthrough{\lstinline!Callable[[T], R]!}). * \textbf{Covariance}: The
container type preserves the subtype relationship:
\[A \subseteq B \implies F(A) \subseteq F(B)\] In Python, this is
defined via \passthrough{\lstinline!T = TypeVar('T', covariant=True)!}.
\emph{Example}: \passthrough{\lstinline!Iterable[T]!} is covariant.
Because \passthrough{\lstinline!Dog!} \(\subseteq\)
\passthrough{\lstinline!Animal!},
\passthrough{\lstinline!Iterable[Dog]!} \(\subseteq\)
\passthrough{\lstinline!Iterable[Animal]!}. A list of dogs can be safely
read as a list of animals. * \textbf{Contravariance}: The container type
reverses the subtype relationship:
\[A \subseteq B \implies F(B) \subseteq F(A)\] In Python, this is
defined via
\passthrough{\lstinline!T = TypeVar('T', contravariant=True)!}.
\emph{Example}: \passthrough{\lstinline!Callable[[T], None]!} arguments
are contravariant. A function that accepts any
\passthrough{\lstinline!Animal!} can be safely used where a function
accepting a \passthrough{\lstinline!Dog!} is expected:
\[\text{Callable[[Animal], None]} \subseteq \text{Callable[[Dog], None]}\]
* \textbf{Invariance}: There is no relationship between container types:
\[F(A) \not\subseteq F(B) \quad \text{and} \quad F(B) \not\subseteq F(A)\]
In Python, standard generic classes are invariant by default.
\emph{Example}: \passthrough{\lstinline!List[T]!} is invariant because
it allows both read (covariant) and write (contravariant) operations.
Allowing a list of dogs to be treated as a list of animals could let
someone insert a cat into the list, violating type safety.

\hypertarget{liskov-substitution-principle-lsp}{%
\subsubsection{2. Liskov Substitution Principle
(LSP)}\label{liskov-substitution-principle-lsp}}

The variance of function arguments and return values is derived from the
\textbf{Liskov Substitution Principle}: if \(S\) is a subtype of \(T\),
then objects of type \(T\) may be replaced with objects of type \(S\)
without altering any of the desirable properties of the program.

Applying LSP to function subtypes leads to this mapping:
\[A \subseteq B \text{ and } C \subseteq D \implies (B \to C) \subseteq (A \to D)\]
This implies that for a function to substitute another: 1.
\textbf{Arguments must be Contravariant}: It must accept a broader set
of inputs. (Narrowing input scope is unsafe). 2. \textbf{Return values
must be Covariant}: It must guarantee a narrower set of outputs.
(Broadening output scope is unsafe).

\begin{lstlisting}
Liskov Function Subtyping Mapping:
Input (Contravariant):   Animal (Parent)  ----->   Dog (Child)
                                                     |
                                                     v
Output (Covariant):       Dog (Child)     ----->   Animal (Parent)
\end{lstlisting}

\hypertarget{compile-time-type-erasure}{%
\subsubsection{3. Compile-Time Type
Erasure}\label{compile-time-type-erasure}}

CPython compiles type annotations into bytecode, but completely ignores
them during execution (unless checked by runtime libraries via
\passthrough{\lstinline!\_\_annotations\_\_!}). Static type checking is
entirely completed during pre-run compilation. Once bytecode is emitted,
generic variables (e.g.~\passthrough{\lstinline!List[int]!}) revert back
to standard untyped collections (e.g.~\passthrough{\lstinline!List!}) in
memory, ensuring that typing extensions introduce zero runtime memory
overhead.
