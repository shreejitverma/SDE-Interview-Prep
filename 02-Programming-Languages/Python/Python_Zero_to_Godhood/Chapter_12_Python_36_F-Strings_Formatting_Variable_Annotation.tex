\hypertarget{pep-498-formatted-string-literals-f-strings}{%
\subsection{12.1 PEP 498: Formatted String Literals
(f-strings)}\label{pep-498-formatted-string-literals-f-strings}}

Python 3.6 introduced Formatted String Literals, commonly referred to as
\textbf{f-strings}, to provide a clean, readable, and highly performant
mechanism for string interpolation.

\hypertarget{legacy-formatting-overheads}{%
\subsubsection{1. Legacy Formatting
Overheads}\label{legacy-formatting-overheads}}

Prior to Python 3.6, developers relied on \passthrough{\lstinline!\%!}
(printf-style) formatting or the \passthrough{\lstinline!.format()!}
string method. Both approaches introduce significant runtime overhead: *
\textbf{Percent (\passthrough{\lstinline!\%!}) Formatting}: Uses ancient
C-style printf routines. It is structurally rigid, struggles to handle
complex container types gracefully, and requires allocating temporary
tuples for positional parameters. * \textbf{Format Method
(\passthrough{\lstinline!.format()!})}: Introduces two major layers of
overhead: 1. \textbf{Attribute Resolution}: Evaluating
\passthrough{\lstinline!"\{\}".format(x)!} requires calling the
\passthrough{\lstinline!\_\_getattribute\_\_!} method on the string
object to locate the \passthrough{\lstinline!.format!} method. 2.
\textbf{Function Call Overhead}: Invoking
\passthrough{\lstinline!.format()!} pushes a new CPython call frame onto
the stack, builds temporary positional arguments tuple
\passthrough{\lstinline!*args!} and keyword arguments dictionary
\passthrough{\lstinline!**kwargs!}, and parses the format string
\emph{at runtime} on every single invocation.

\hypertarget{f-string-compilation-mechanics}{%
\subsubsection{2. f-String Compilation
Mechanics}\label{f-string-compilation-mechanics}}

f-strings bypass these overheads by converting interpolation directly
into optimized bytecode operations at compile time. When the CPython
parser encounters an f-string
(e.g.~\passthrough{\lstinline!f"Name: \{name\}, Age: \{age\}"!}), it
parses the literal components and the embedded expressions into separate
AST nodes: 1. \textbf{Static Literal Sections}: Treated as constant
string literals. 2. \textbf{Embedded Expressions}: Extracted, parsed as
separate AST sub-trees, and compiled into standard bytecode instruction
sequences.

The compiler generates two primary bytecode instructions to handle
f-strings: * \textbf{\passthrough{\lstinline!FORMAT\_VALUE!}}: Pops a
value off the stack, applies formatting parameters (str/repr/ascii
conversion or formatting specifiers), and pushes the formatted string
back onto the stack. * \textbf{\passthrough{\lstinline!BUILD\_STRING!}}:
Pops a specified number of strings off the stack, performs a
high-performance C-level string concatenation
(\passthrough{\lstinline!PyUnicode\_Concat!} or pre-allocated buffer
copy), and pushes the final concatenated string onto the stack.

\hypertarget{cpython-format_value-flag-specification}{%
\paragraph{\texorpdfstring{CPython \texttt{FORMAT\_VALUE} Flag
Specification:}{CPython FORMAT\_VALUE Flag Specification:}}\label{cpython-format_value-flag-specification}}

The \passthrough{\lstinline!FORMAT\_VALUE!} instruction takes an 8-bit
integer argument representing rendering flags: *
\passthrough{\lstinline!0x00!}: No conversion (calls
\passthrough{\lstinline!\_\_format\_\_!} directly). *
\passthrough{\lstinline!0x01!}: Call \passthrough{\lstinline!str()!}
(corresponding to the \passthrough{\lstinline"!s"} flag). *
\passthrough{\lstinline!0x02!}: Call \passthrough{\lstinline!repr()!}
(corresponding to the \passthrough{\lstinline"!r"} flag). *
\passthrough{\lstinline!0x04!}: Call \passthrough{\lstinline!ascii()!}
(corresponding to the \passthrough{\lstinline"!a"} flag). *
\passthrough{\lstinline!0x08!}: Have a format specifier. If this bit is
set, the instruction pops two values from the stack: the format
specifier string (e.g., \passthrough{\lstinline!".2f"!}) followed by the
value to format.

\hypertarget{bytecode-disassembly-analysis}{%
\subsubsection{3. Bytecode Disassembly
Analysis}\label{bytecode-disassembly-analysis}}

Let's analyze the difference in compilation between
\passthrough{\lstinline!.format()!} and an f-string:

\begin{lstlisting}[language=Python]
import dis

def legacy_format(name, age):
    return "Name: {}, Age: {}".format(name, age)

def fstring_format(name, age):
    return f"Name: {name!r:10}, Age: {age}"
\end{lstlisting}

\hypertarget{disassembly-of-legacy_format}{%
\paragraph{\texorpdfstring{Disassembly of
\texttt{legacy\_format}:}{Disassembly of legacy\_format:}}\label{disassembly-of-legacy_format}}

\begin{lstlisting}
  2           0 LOAD_CONST               1 ('Name: {}, Age: {}')
              3 LOAD_ATTR                0 (format)
              6 LOAD_FAST                0 (name)
              9 LOAD_FAST                1 (age)
             12 CALL_FUNCTION            2
             15 RETURN_VALUE
\end{lstlisting}

\emph{Note}: \passthrough{\lstinline!LOAD\_ATTR!} and
\passthrough{\lstinline!CALL\_FUNCTION!} demonstrate the high overhead
of method lookup and frame creation at runtime.

\hypertarget{disassembly-of-fstring_format}{%
\paragraph{\texorpdfstring{Disassembly of
\texttt{fstring\_format}:}{Disassembly of fstring\_format:}}\label{disassembly-of-fstring_format}}

\begin{lstlisting}
  5           0 LOAD_CONST               1 ('Name: ')
              3 LOAD_FAST                0 (name)
              6 FORMAT_VALUE             2              /* repr (!r) conversion flag */
              9 LOAD_CONST               2 ('10')       /* Format specifier string */
             12 FORMAT_VALUE             10             /* Flag 0x02 (repr) + 0x08 (has spec) = 10 */
             15 LOAD_CONST               3 (', Age: ')
             18 LOAD_FAST                1 (age)
             21 FORMAT_VALUE             0              /* Default formatting */
             24 BUILD_STRING             5              /* Concatenate the 5 stack items */
             27 RETURN_VALUE
\end{lstlisting}

Because the VM calculates the lengths of all strings in the stack,
\passthrough{\lstinline!BUILD\_STRING 5!} pre-allocates a single
contiguous memory block in the C heap and copies the characters
directly, completely avoiding intermediate string allocations and
Python-level function calls.

\hypertarget{pep-526-syntax-for-variable-annotations}{%
\subsection{12.2 PEP 526: Syntax for Variable
Annotations}\label{pep-526-syntax-for-variable-annotations}}

PEP 526 introduced variable type annotations to complement the function
parameter annotations defined in PEP 3107.

\hypertarget{class-and-module-level-annotations}{%
\subsubsection{1. Class and Module Level
Annotations}\label{class-and-module-level-annotations}}

At the module or class level, type annotations are evaluated at module
import or class definition time. 1. The compiler evaluates the annotated
type expression. 2. It creates or updates a dictionary named
\passthrough{\lstinline!\_\_annotations\_\_!} in the module or class
namespace. 3. The type annotation metadata is stored inside this
dictionary:
\passthrough{\lstinline!\{'variable\_name': type\_object\}!}.

Let's examine how the CPython compiler compiles a class with variable
annotations:

\begin{lstlisting}[language=Python]
class Profile:
    name: str = "Anonymous"
    age: int
\end{lstlisting}

\hypertarget{compiled-bytecode-for-profile-class-namespace-creation}{%
\paragraph{\texorpdfstring{Compiled Bytecode for \texttt{Profile} class
namespace
creation:}{Compiled Bytecode for Profile class namespace creation:}}\label{compiled-bytecode-for-profile-class-namespace-creation}}

\begin{lstlisting}
  1           0 LOAD_NAME                0 (__name__)
              3 STORE_NAME               1 (__module__)
              6 LOAD_CONST               0 ('Profile')
              9 STORE_NAME               2 (__qualname__)
             12 SETUP_ANNOTATIONS                       /* Initializes class __annotations__ */
             15 LOAD_NAME                3 (str)
             18 LOAD_NAME                4 (__annotations__)
             21 LOAD_CONST               1 ('name')
             24 STORE_SUBSCR                            /* Store name: str in __annotations__ */
             25 LOAD_CONST               2 ('Anonymous')
             28 STORE_NAME               5 (name)
             31 LOAD_NAME                6 (int)
             34 LOAD_NAME                4 (__annotations__)
             37 LOAD_CONST               3 ('age')
             40 STORE_SUBSCR                            /* Store age: int in __annotations__ */
             41 LOAD_CONST               4 (None)
             44 RETURN_VALUE
\end{lstlisting}

\begin{itemize}
\tightlist
\item
  \textbf{\passthrough{\lstinline!SETUP\_ANNOTATIONS!}}: Emitted by the
  compiler to initialize the
  \passthrough{\lstinline!\_\_annotations\_\_!} dictionary in the active
  namespace if it does not already exist.
\item
  \textbf{\passthrough{\lstinline!STORE\_SUBSCR!}}: Updates
  \passthrough{\lstinline!\_\_annotations\_\_!} dynamically at runtime,
  showing that class-level annotations do carry a small runtime
  initialization overhead.
\end{itemize}

\hypertarget{function-level-variable-annotations}{%
\subsubsection{2. Function-Level Variable
Annotations}\label{function-level-variable-annotations}}

In contrast to classes and modules, variable annotations defined inside
function scopes are \textbf{completely ignored} at runtime:

\begin{lstlisting}[language=Python]
def process():
    x: int = 42
\end{lstlisting}

\hypertarget{disassembly-of-process}{%
\paragraph{\texorpdfstring{Disassembly of
\texttt{process}:}{Disassembly of process:}}\label{disassembly-of-process}}

\begin{lstlisting}
  2           0 LOAD_CONST               1 (42)
              3 STORE_FAST               0 (x)
              6 LOAD_CONST               0 (None)
              9 RETURN_VALUE
\end{lstlisting}

Notice that there are no type checks, no
\passthrough{\lstinline!SETUP\_ANNOTATIONS!}, and no
\passthrough{\lstinline!\_\_annotations\_\_!} dictionary overhead. The
type annotation metadata \passthrough{\lstinline!int!} is entirely
stripped by the compiler. This ensures that function execution paths
(which are executed frequently) maintain maximum speed and zero memory
allocation overhead.

\hypertarget{forward-references-and-runtime-inspection}{%
\subsubsection{3. Forward References and Runtime
Inspection}\label{forward-references-and-runtime-inspection}}

Because class/module annotations are executed at definition time,
declaring a type that has not yet been defined will raise a
\passthrough{\lstinline!NameError!}:

\begin{lstlisting}[language=Python]
class Node:
    parent: Node  # Raises NameError: name 'Node' is not defined
\end{lstlisting}

To bypass this, developers use string literals (forward references):

\begin{lstlisting}[language=Python]
class Node:
    parent: 'Node'  # Compiles successfully as a string literal
\end{lstlisting}

At runtime, frameworks inspect these annotations using
\passthrough{\lstinline!inspect.get\_type\_hints()!} or
\passthrough{\lstinline!typing.get\_type\_hints()!}. These utilities
automatically resolve string-based forward references by evaluating them
within the global and local namespace of the target class or module.

\hypertarget{cpython-compact-dictionary-design}{%
\subsection{12.3 CPython Compact Dictionary
Design}\label{cpython-compact-dictionary-design}}

Python 3.6 replaced CPython's legacy dictionary layout with a compact,
ordered representation proposed by Raymond Hettinger.

\hypertarget{legacy-dictionary-layout-pre-3.6}{%
\subsubsection{1. Legacy Dictionary Layout
(Pre-3.6)}\label{legacy-dictionary-layout-pre-3.6}}

Historically, a CPython dictionary was implemented as a single, large
sparse hash table. Every slot in the table contained a 24-byte
\passthrough{\lstinline!PyDictKeyEntry!} structure:

\begin{lstlisting}[language=C]
typedef struct {
    Py_hash_t me_hash;   /* 8 bytes */
    PyObject *me_key;    /* 8 bytes */
    PyObject *me_value;  /* 8 bytes */
} PyDictKeyEntry;
\end{lstlisting}

To maintain \(O(1)\) lookups, the hash table was kept sparse with a
maximum fill factor of 2/3. For a dictionary containing 8 entries,
CPython had to allocate a table of at least 16 slots. * \textbf{Memory
Overhead}: Each empty slot in the table required 24 bytes of memory. If
a dictionary was large, the amount of wasted memory in unallocated slots
was massive:
\[\text{Wasted Memory} = \text{Empty Slots} \times 24 \text{ bytes}\]

\hypertarget{legacy-sparse-array-layout}{%
\paragraph{Legacy Sparse Array
Layout:}\label{legacy-sparse-array-layout}}

\begin{lstlisting}
Indices/Entries Table (Sparse):
[ Slot 0: Hash | Key* | Val* ] (24 bytes)
[ Slot 1: NULL | NULL | NULL ] (Wasted 24 bytes)
[ Slot 2: Hash | Key* | Val* ] (24 bytes)
[ Slot 3: NULL | NULL | NULL ] (Wasted 24 bytes)
[ Slot 4: Hash | Key* | Val* ] (24 bytes)
\end{lstlisting}

\hypertarget{the-compact-dictionary-layout}{%
\subsubsection{2. The Compact Dictionary
Layout}\label{the-compact-dictionary-layout}}

The new design splits the dictionary into two separate arrays: 1.
\textbf{\passthrough{\lstinline!dk\_indices!} (Sparse Index Array)}: A
small, sparse array containing integers (indices pointing into the dense
array). Depending on the dictionary size, each index is stored as a
1-byte (\passthrough{\lstinline!int8\_t!}), 2-byte
(\passthrough{\lstinline!int16\_t!}), or 4-byte
(\passthrough{\lstinline!int32\_t!}) integer. 2.
\textbf{\passthrough{\lstinline!dk\_entries!} (Dense Entry Array)}: A
dense, contiguous array containing
\passthrough{\lstinline!PyDictKeyEntry!} structures (24 bytes each).
Every slot in this array is fully packed in the order keys are inserted.

\hypertarget{compact-array-layout-cpython-3.6}{%
\paragraph{Compact Array Layout (CPython
3.6+):}\label{compact-array-layout-cpython-3.6}}

\begin{lstlisting}
dk_indices (Sparse Array of int8_t):
[ 0 | -1 | 1 | -1 | 2 ]  (5 bytes, where -1 represents an empty slot)

dk_entries (Dense Array of PyDictKeyEntry):
[ Slot 0: Hash | Key* | Val* ] (24 bytes) - Inserts first
[ Slot 1: Hash | Key* | Val* ] (24 bytes) - Inserts second
[ Slot 2: Hash | Key* | Val* ] (24 bytes) - Inserts third
\end{lstlisting}

\hypertarget{dynamic-lookup-walkthrough}{%
\paragraph{Dynamic Lookup
Walkthrough:}\label{dynamic-lookup-walkthrough}}

To look up a key (e.g.~looking up \passthrough{\lstinline!key!} with
hash value mapped to sparse index \passthrough{\lstinline!2!}): 1.
CPython computes the key's hash and hashes it to a slot in
\passthrough{\lstinline!dk\_indices!}. 2. If
\passthrough{\lstinline!dk\_indices[hash\_slot]!} is
\passthrough{\lstinline!1!}, it retrieves the entry at
\passthrough{\lstinline!dk\_entries[1]!}. 3. It compares the keys. If
matched, it returns the value. If there is a collision, it continues
probing within the sparse \passthrough{\lstinline!dk\_indices!} array.

\hypertarget{core-structural-implications}{%
\subsubsection{3. Core Structural
Implications}\label{core-structural-implications}}

\begin{itemize}
\tightlist
\item
  \textbf{Memory Savings}: Instead of wasting 24 bytes per empty slot,
  CPython now only wastes 1, 2, or 4 bytes per empty slot in
  \passthrough{\lstinline!dk\_indices!}. This layout reduces dictionary
  memory footprints by \textbf{30\% to 40\%} in real-world workloads.
\item
  \textbf{Preservation of Insertion Order}: Because entries are appended
  to \passthrough{\lstinline!dk\_entries!} contiguously, the elements
  are stored in their exact insertion order. Iteration over the
  dictionary simply traverses the dense
  \passthrough{\lstinline!dk\_entries!} array sequentially.
\item
  \textbf{Faster Iteration}: Traversal does not require skipping empty
  slots, making dictionary iteration significantly faster due to CPU
  cache line friendliness.
\item
  \textbf{Language Specification Guarantee}: While insertion order was
  introduced as an implementation detail in Python 3.6, it was
  officially codified as a language specification guarantee in Python
  3.7.
\end{itemize}
